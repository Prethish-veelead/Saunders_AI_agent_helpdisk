How a question is answered

Three sources, checked in order

Every question is checked against three sources, in a fixed order, and the first one that gives a genuinely complete answer wins:

  1. Closed or resolved tickets. A real support conversation that already reached a working resolution is usually the best possible answer — more specific and more trusted than general documentation.
  2. Your website. If tickets don't answer it, the assistant reads your tracked web pages directly — no external search engine involved (see the companion brief, Live URL Search, for the full detail on this one).
  3. Library documents + tickets, combined. If neither of the above answers it, a broader search across your full knowledge library and ticket history runs as the last resort.
Quality safeguard

A ticket being "closed" doesn't automatically mean its notes are useful — a resolution like "escalated to network team" or "fixed on my end" doesn't actually help the next person. The assistant checks for this: if a ticket's own content wouldn't genuinely let someone fix the issue themselves, it's treated the same as not finding an answer at all, and the system moves on to the website or library instead of showing an unhelpful note.

Source accuracy safeguard

Every answer is checked against exactly which reference document GPT-4o actually drew from — not just whichever result scored highest in search. This is what stops a user from ever seeing, say, a ticket link cited next to an answer that actually came from a library document.

Multi-turn support

It remembers the conversation

A follow-up question like "is it good for gaming?" only makes sense in light of what was just asked. The assistant supports this: each request can include the prior question-and-answer pairs from the same conversation, and it uses them to understand what a follow-up actually means — resolving "it," "that one," "the second option," and similar references to whatever they point back to.

The service itself is stateless — it doesn't store or remember anything between requests. Whatever app or chat widget is talking to it is responsible for resending the relevant prior turns each time. This keeps the backend simple and puts conversation history entirely under your own app's control.

What it's built on

The stack

Azure Functions

Runs everything — Python, Linux, Consumption plan. No server to manage, and no cost while idle.

Azure AI Search — Basic

The searchable index behind tickets and library documents — combines keyword matching with meaning-based (vector) search in one query.

Azure OpenAI — GPT-4o

Writes every final answer, and reports exactly which source it used — the only model involved in generating a response.

Azure OpenAI — text-embedding-3-large

Converts tickets, documents, and questions into the vector form the meaning-based search relies on.

Microsoft Graph / SharePoint

Source of truth for tickets, library documents, and tracked website URLs. Connected via a Managed Identity — no client secret stored anywhere.

requests + BeautifulSoup + RapidFuzz

Powers the website-crawl search — plain HTTP fetches and local text matching, no external search provider or API.

Application Insights

Monitoring and diagnostics — every request, sync run, and error is logged and queryable.

Both are editable by your own team, with no code change and no developer needed: Azure Portal → the Function App → Settings → Environment variables → edit the value → Save. Each sync only processes items that are new or have actually changed since last time, so running it every 15 minutes costs no more than running it once a day would — nothing gets needlessly re-processed.
