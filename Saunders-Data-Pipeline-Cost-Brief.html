Platform choice

Every Azure resource in this system was picked for a specific reason, not by default:

ServiceWhy this one

Consumption plan		 No server to provision, patch, or pay for while idle. A helpdesk's traffic is bursty — busy during work hours, near-silent overnight — and Consumption billing matches that shape exactly: you pay per execution, not per hour of an always-on machine.

1 — Initial capture

Where data is saved

Nothing is copied into a separate raw-file store. SharePoint stays the single system of record for everything — tickets, ticket comments, and library documents. Each sync run reads directly from SharePoint (via Microsoft Graph), and the only thing that gets written anywhere new is the processed, searchable version described below — the original document or ticket is never duplicated or modified.

This means there's exactly one place your team edits content — SharePoint itself — and the assistant's knowledge simply catches up on the next scheduled sync.

2 — Ingestion pipeline

How data is processed

All of this runs as Azure Function executions — inside Azure's own compute, in the Australia East region, the same region as every other resource in this system. Nothing is processed on any local machine or outside Azure.

Before anything is embedded, plain text has to be pulled out of whatever format the source document is in:

FormatExtracted with
.pdfpdfplumber — reads text page by page
.docxpython-docx — reads each paragraph
.htmltrafilatura — strips markup, keeps the real content
.mdMarkdown → HTML → plain text
.pptxpython-pptx — reads text from every slide
Ticket fieldsNo extraction needed — subject, description, and comments are already plain text

Once it's plain text, it's split into overlapping chunks: 1,000 characters each, with 150 characters shared between consecutive chunks, always breaking on a word boundary rather than mid-word. The overlap exists so a fact sitting right at a chunk boundary is still fully readable from at least one chunk — nothing gets awkwardly cut in half.

Chunk 1 — characters 0–1,000
Chunk 2 — characters 850–1,850
↑ 150-character overlap ↑

Chunk 2 starts 850 characters into the text (1,000 − 150 overlap), so the last 150 characters of chunk 1 reappear at the start of chunk 2. Every chunk after the first works the same way.

Before any of this runs, a SHA-256 hash of the entire document's text is compared against the hash stored from the last successful sync. If they match, nothing changed — the whole extract/chunk/embed sequence is skipped entirely for that document. This is what keeps a 15-minute ticket sync cheap: most runs find nothing new to do.

3 — The index

Where data — and embeddings — are stored

Every chunk becomes one record in the Azure AI Search index (saunders-ai-search), with:

  • Its text content and title, both keyword-searchable
  • Its embedding — a list of 3,072 numbers — stored directly on that same record, in a dedicated vector field. There's no separate "embeddings database"; the vector lives right alongside the text it was generated from.
  • source_type — ticket, library_doc, or live_url — so a search can be restricted to just one
  • content_hash — the dedup fingerprint described above
  • Category, sub-category, status, and source URL, for filtering and citation

The vector field uses an algorithm called HNSW, which is what lets a meaning-based search return in milliseconds even as the index grows — it doesn't have to compare against every single chunk one by one. This entire index — and everything it stores — lives inside your own Azure subscription, in Australia East; it isn't a third-party or shared service.

4 — Keeping the index honest

Adding, updating, and deleting content

Every sync run reconciles the index against whatever is currently in SharePoint at that moment — it isn't purely additive:

ADDED

Picked up on the very next scheduled sync (≤15 min for tickets, ≤1 hour for library docs) — chunked, embedded, and indexed automatically. No action needed from your team.

EDITED

The content fingerprint (SHA-256 hash) no longer matches what was indexed last time, so the document is fully re-chunked, re-embedded, and re-indexed with the new content on the next sync, replacing the old version.

DELETED

Every sync compares the full list of items currently in SharePoint against what's currently indexed. Anything indexed that's no longer present — or, for tickets specifically, no longer Closed/Resolved (e.g. reopened) — has every one of its chunks removed from the index on that same run. Nothing is left waiting for manual cleanup.

One nuance worth flagging

An edit that keeps a document roughly the same length (or makes it longer) is replaced cleanly with no trace of the old version. In the less common case where an edit makes a document much shorter — few enough chunks that the new version has fewer pieces than the old one did — the re-index step overwrites the chunks that still exist, but doesn't separately go back and remove the small number of extra chunks left over from the longer previous version. This is a minor edge case, not something we've seen cause a visible issue, and it fully resolves itself the moment that document is eventually deleted outright. Flagging it here for full transparency, not as an active problem.

5 — Retrieval

How search works — stored vs. live

The key distinction

Tickets and library documents are always answered from the stored, pre-synced index — never a live lookup against SharePoint at the moment someone asks. That's what keeps those answers fast: a search query against an already-built index, not a round-trip to SharePoint itself. The only part of the system that does anything "live" is Tier 2 — your website — covered in full below.

For tickets and library docs, every question runs through one search call that combines two techniques at once:

  • Keyword search — the classic "does this text contain these words" match
  • Vector search — the question is embedded the same way documents are, then compared by meaning, so a question can match a chunk that never uses the exact same words

Azure AI Search fuses both result sets into one ranking automatically. The top 5 matching chunks come back; up to 3 make it into the final answer's cited sources.

How the system decides which tier to use

There's no upfront step that classifies a question as "this is a website question" or "this is a library question." Instead, all three tiers are simply tried in a fixed order on every single question — tickets, then website, then library + tickets combined — and whichever one is the first to produce a genuinely complete answer is used. The others are never even attempted once one succeeds. If a topic happens to live in both a ticket and the library, the ticket wins every time, purely because it's tried first — not because of any smarter routing decision.

6 — Tier 2, in depth

Web URL search

This is the one search path that never touches the index, never calls the embedding model, and never asks a third-party search engine anything. Every time it runs, it goes out and reads your actual tracked pages fresh:

Details worth knowing:

  • Crawl. Every tracked page's own links are followed too (up to 30 per tracked page), as long as they point to the same website. Links to social media, login pages, shopping carts, and search-result pages are filtered out automatically — they'd otherwise pollute the results with generic titles like "Search" or "Cart."
  • Rank. Every candidate page's title is scored against the question using local fuzzy text matching (a library called RapidFuzz) — this step costs nothing and takes milliseconds, since it's plain text comparison, not an AI call.
  • Fetch content. Only the top 2 ranked pages get their full text downloaded and cleaned up (navigation menus, footers, and scripts stripped out) — not the whole website, keeping this step fast even on a large site.
  • Generate. GPT-4o gets those 2 pages' real text and must answer strictly from it, reporting exactly which one the answer actually came from — the same citation safeguard used everywhere else in the system.
Known limitation

The crawl currently goes one level deep from each tracked URL. A question that needs a very specific sub-page — one that's itself linked from a page the crawl already found, two clicks from the original tracked URL — may not be found. This mostly affects narrow, multi-part questions. A second crawl level is a straightforward addition if this turns out to matter often enough in practice.

7 — Answering

How responses are generated

Whichever tier finds a match hands its results — as numbered reference chunks — to GPT-4o in a single call, with strict instructions: answer only from what's here, and report exactly which numbered reference the answer actually came from. That self-reported number is what decides the source shown to the user, not just whichever chunk happened to score highest in search — this is the fix that stops a ticket link from ever being shown next to an answer that actually came from a library document.

If the caller includes prior turns from the same conversation, GPT-4o also uses those to understand what the current question means (resolving "it," "that one," and similar) — but never as a substitute for the actual reference content. And a closed ticket that's merely on-topic, without giving a real usable fix, is treated the same as no answer at all, so a better source gets a real chance further down the chain.

9 — Cost formula

Embedding cost per document

The formula behind every number in this document:

characters ÷ 4 ≈ tokens, then tokens × $0.13 per 1,000,000 = embedding cost

($0.13/1M tokens is Microsoft's published rate for text-embedding-3-large, Australia East, at the time of writing.)

Apply it to any document: estimate its character count, divide by 4 for a token estimate, multiply by the rate above. The worked example below walks through exactly this for a realistic document.

10 — Full worked example

A 30-page document, start to finish

Assuming a typical business document at roughly 3,000 characters per page (~500 words/page — actual density varies by document):

Total text — 30 pages × 3,000 characters90,000 characters
Chunks — 1,000 chars each, 850-char step after the first≈ 106 chunks
Tokens embedded — 106 chunks × ~250 tokens≈ 26,500 tokens
Embedding cost — 26,500 × $0.13 / 1,000,000≈ $0.0034
Storage — 106 chunks × ~13KB (vector + text)≈ 1.4 MB
Total cost to fully embed and index this document ≈ $0.0034

That's roughly a third of a cent — one-time, at first sync. What happens afterward:

  • Every re-sync of this same document, unchanged: $0 — the SHA-256 dedup check skips it entirely, whether the sync runs every 15 minutes or once a week.
  • Every search that happens to match this document: effectively $0 marginal cost — search queries are covered by the fixed Azure AI Search monthly fee, not billed per query. The only real cost is the same GPT-4o generation cost as any other question (≈$0.015, as established in the companion overview) — this document being one of many candidates changes nothing about that cost.
  • Storage: ~1.4MB is a rounding error against the index's overall capacity — thousands of documents this size fit comfortably within the Basic tier.
The one real trade-off

The 150-character overlap between chunks means a small amount of text gets embedded twice on purpose — this is what the "chunks × ~250 tokens" math above already includes. It's a deliberate design choice: slightly higher embedding cost (a fraction of a cent either way) in exchange for never losing a fact that happens to sit right at a chunk boundary.
