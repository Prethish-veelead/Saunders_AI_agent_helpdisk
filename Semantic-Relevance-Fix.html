Engineering Report

Semantic Relevance Fix

Why website search sometimes picked the wrong page — or the wrong site entirely — for real questions, and the two-part fix that replaced literal word-matching with meaning-based matching.

Prepared for: Engineering lead review Component: Website search (Tier 2) Status: Fixed, tested, deployed
The problem

Same question, worded differently, different answer

Testing surfaced three real, reproducible cases where the assistant either answered from the wrong page, or found nothing at all, even though the right content genuinely existed on a tracked site:

Case 1 — a rephrased question failed entirely

Before
"What screen sizes are available for Lenovo laptops?"

→ "No answer found for your query."

Same question, different words
"screen sizes of lenovo laptop"

→ Answered correctly, with the real spec list.

Case 2 — a follow-up question the assistant itself suggested, failed

After answering a question about Python, the assistant suggested "What are the major implementations of Python?" as a follow-up. Clicking it returned nothing. The actual candidate ranking showed why:

Old method scored this #1 — 100.0
"Programming language implementation"

A generic Wikipedia article about what "implementation" means in software — nothing to do with Python specifically.

The actual right page — crowded out entirely
"Python (programming language)"

Didn't even make the shortlist, despite covering Python's real implementations (CPython, PyPy, etc).

Case 3 — one relevant site crowded out another, equally relevant, site

For a generic "tell me about laptops" question, every top result came from one tracked laptop retailer site — a second tracked site, Lenovo's own site, never appeared at all, even though it obviously sells laptops.

Root cause

The old method compared words, not meaning

Website search decided which page to use by comparing literal text — closer to a spell-checker than real understanding. In Case 2 above, the question contains the word "implementations", and a page literally titled "Programming language implementation" matches that word almost perfectly — so it won, even though it's not about Python at all. The actual Python article, which uses the word "implementations" less directly, scored lower and got dropped.

This is a structural limitation, not a one-off glitch: text-matching has no way to know that "Lenovo" is a laptop brand, or that a rephrased question means the same thing as the original. Every case above traces back to this same root cause.

The fix, part 1 of 2
Part 1 — Which site is relevant

Deciding by meaning which tracked site to even look at

Before crawling anything, each tracked site's name is compared against the question using an embedding — the same AI technique already used elsewhere in this system to search tickets and library documents, now applied here too. An embedding turns text into a set of numbers that represents its meaning, so "Lenovo" and "laptop" can be recognized as related even though they share no letters in common.

01
Tracked sites
Lenovo, laptop retailer, Python wiki, etc.
→
02
Compare by meaning
Embedding similarity, not shared words
→
03
Keep what's relevant
Only crawl sites that clear the bar
→
04
Safety net
Nothing clears it? Keep everything.

Real result for "tell me about laptops": both the Lenovo site and the laptop retailer site are now correctly identified as relevant — where before, one crowded the other out entirely.

Built with scale in mind, not just today's fix

Right now there are only 4 tracked sites, so this mostly fixes site-crowding. Once the client adds many more tracked sites, crawling every single one for every question stops being practical — this same step is what will keep that fast, by ruling out irrelevant sites before any crawling happens at all, rather than after.

The fix, part 2 of 2
Part 2 — Which page within that site

Deciding by meaning which specific page answers the question

Once the relevant site(s) are chosen, their pages get crawled exactly as before. The change is in how the best page is picked: instead of comparing literal words, each candidate page's title is compared to the question the same way — by meaning, using an embedding.

This is the part that directly fixes Case 2. Re-run today, the ranking for "What are the major implementations of Python?" now looks like this:

RankPageResult
1stCPythonCorrect — CPython is literally one of the major implementations
2ndPython (programming language)Correct — the main article, covers implementations directly

The generic "Programming language implementation" article that previously won no longer even competes, once the site-level step above already narrowed things down to the Python site specifically.

Verification

How this was tested before being called done

Every fix in this project gets tested against the real, original failure before being considered resolved — not just re-checked in theory:

  • 1 Case 1 (rephrased Lenovo question) — re-run live ✓ Fixed
  • 2 Case 2 (Python follow-up question) — re-run live, full click-through ✓ Fixed
  • 3 Case 3 (Lenovo vs. retailer site-crowding) — both sites now correctly identified ✓ Fixed
  • 4 Previously-working questions re-tested, to confirm nothing broke ✓ No regression
  • 5 6 new automated tests, plus the full existing test suite (60+ checks) ✓ All passing

The relevance threshold used in Part 1 wasn't guessed — it was calibrated against real questions and the real tracked sites before deployment, specifically checking that it never excludes something genuinely relevant.

Where this stands

Deployed and live

Both parts are deployed to the test environment and to the client's live system. On the client side specifically, this stays dormant for now — they haven't configured any tracked website URLs yet — but it's in place and tested, ready as soon as that happens.
